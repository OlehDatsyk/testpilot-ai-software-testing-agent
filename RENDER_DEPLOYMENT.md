# Render Deployment

> **Status: prepared, not deployed.** The Blueprint (`render.yaml`) was written against the current Render Blueprint specification (https://render.com/docs/blueprint-spec, checked 2026-11-08) and the backend image/start command were verified locally in Docker. No live Render deployment has been performed, so live behaviour is **NOT TESTED**.

## Architecture on Render

| Service | Render type | Plan in Blueprint | Purpose |
|---|---|---|---|
| `testpilot-frontend` | Static Site | free | React SPA (`frontend/dist`), SPA rewrite `/* → /index.html` |
| `testpilot-api` | Python Web Service | free | FastAPI + embedded job thread (`RUN_WORKER_IN_API=true`) |
| `testpilot-database` | Render Postgres | free | metadata, jobs, results |
| `testpilot-worker` | — | not created | optional; see "Separate worker" below |

**Test execution is disabled on Render** (`EXECUTION_PROVIDER=disabled`). Render services are not a sandbox for untrusted code and offer no Docker daemon. Users can still import repositories, run static analysis, generate and review tests, create bug reports, use the assistant and generate reports; runs are recorded as *Execution unavailable*. Configuration validation prevents enabling the embedded worker together with any execution provider.

## 1. Account & GitHub
1. Create a Render account and connect your GitHub account (Render dashboard → *Account settings → Git providers*).
2. Push this repository to GitHub (see the publication commands in the release notes).

## 2. Create the Blueprint
1. Dashboard → **New → Blueprint** → select the repository. Render reads `render.yaml`.
2. Review the three resources. Choose a region if `frankfurt` is not appropriate — services and database must share a region, and the region cannot be changed later.
3. Enter the `sync: false` values when prompted (they are only requested on the first sync):

| Variable | Service | Value |
|---|---|---|
| `FRONTEND_URL` | api | `https://testpilot-frontend.onrender.com` (your actual static-site URL) |
| `CORS_ORIGINS` | api | same as `FRONTEND_URL` |
| `VITE_API_BASE_URL` | frontend | `https://testpilot-api.onrender.com` (your actual API URL) — public, build-time |
| `AI_API_KEY` | api | optional — leave empty to keep AI disabled |
| `TOKEN_ENCRYPTION_KEY` | api | optional Fernet key |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` / `GITHUB_REDIRECT_URI` | api | optional — see §4 |

`SECRET_KEY` is generated by Render (`generateValue`). `DATABASE_URL` comes from the database (`fromDatabase … connectionString`); `postgres://` URLs are normalised to the psycopg driver automatically. If service names are taken, Render assigns different subdomains — update the URL variables and **redeploy the frontend** (Vite bakes `VITE_API_BASE_URL` in at build time).

## 3. Database & migrations
Free web services cannot use `preDeployCommand`, so the API start command runs `alembic upgrade head` before `uvicorn`. Alembic migrations are idempotent and never drop data on upgrade. On a paid plan you may move it to `preDeployCommand: alembic upgrade head`. `AUTO_CREATE_TABLES=false` in production — the schema is managed by migrations only.

## 4. GitHub OAuth (optional)
Create an OAuth App at GitHub → *Settings → Developer settings → OAuth Apps*: Homepage = frontend URL; **Authorization callback URL = `https://<api-host>/api/github/oauth/callback`**. Put the client id/secret and the same callback in the API's variables. Public repositories work without OAuth (60 unauthenticated GitHub API requests/hour per IP — a `GITHUB_PUBLIC_TOKEN` raises this).

## 5. AI provider (optional)
Set `AI_PROVIDER=anthropic` and `AI_API_KEY` on the API service. Without them, AI features report "not configured" and the rule-based/grounded features continue to work.

## 6. Health checks & logs
* Render health check: `GET /health/ready` (checks the database; no analysis or execution; no secrets in the response). `GET /health` is a lightweight liveness probe.
* Logs: each service's *Logs* tab. Credentials are redacted by the application's log filter.
* Verify after deploy: `https://<api>/health/ready` → `{"status":"ready","database":"ok"}`; `https://<api>/api/system/capabilities` shows `execution.available=false`; open the frontend, register, load the demo project.

## 7. Storage limitations
Render's filesystem is ephemeral: `STORAGE_ROOT=/tmp/testpilot-storage` holds snapshots, run logs and generated reports, and is wiped on every deploy/restart (and free services restart when they spin down). Database records survive; files do not — re-import a project or regenerate a report if a download returns 410. For persistence, attach a Render persistent disk (paid; prevents zero-downtime deploys and limits the service to one instance) and point `STORAGE_ROOT` at it, or add object storage (roadmap).

## 8. Separate worker (paid)
For production load, move job processing out of the API:
```yaml
  - type: worker
    name: testpilot-worker
    runtime: python
    plan: 0.5c-512mb
    region: frankfurt
    rootDir: backend
    buildCommand: pip install -r requirements.txt
    startCommand: python -m app.worker
    envVars: # same as testpilot-api (DATABASE_URL, SECRET_KEY via fromService/env group, EXECUTION_PROVIDER=disabled, …)
```
and set `RUN_WORKER_IN_API=false` on the API. Note: API and worker would need **shared storage** for snapshots (a disk can be attached to only one service), so this requires object storage support first — keep the embedded worker until then.

## 9. Execution in production
Run a `docker`-provider worker on infrastructure you control (dedicated VM), sharing the database and the storage volume with the API, and follow [EXECUTION_SECURITY.md](EXECUTION_SECURITY.md). Do not enable execution on Render services.

## 10. Updating & rollback
* Push to the deployed branch → Render auto-deploys (Blueprint changes are applied on sync).
* Rollback: service → *Events* → choose an earlier deploy → **Rollback**. Database migrations are not rolled back automatically; only add backward-compatible migrations, and back up before risky ones.

## 11. Troubleshooting
| Problem | Fix |
|---|---|
| API crashes at start with `SECRET_KEY must be set` | `ENVIRONMENT=production` requires a ≥32-char key — keep `generateValue: true` |
| Browser shows CORS errors | `CORS_ORIGINS` must exactly match the frontend origin (scheme + host, no trailing slash) |
| Frontend calls `localhost:8000` | `VITE_API_BASE_URL` was missing at build time — set it and redeploy the static site |
| Jobs stay queued | `RUN_WORKER_IN_API` must be `true` (or a worker service must run) |
| Build fails on Python version | `PYTHON_VERSION` is pinned to 3.12.10 in the Blueprint |
| First request is slow | free web services spin down when idle; the first request wakes them |

## 12. Costs and free-tier restrictions
Check https://render.com/pricing for current prices. As configured, all three resources use free plans: free web services spin down after inactivity and have limited monthly hours; free Postgres has limited storage and **expires after a fixed period** (30 days at the time of writing) unless upgraded — use a paid database plan (e.g. `0.1c-256mb`) for anything you want to keep. Paid resources (separate worker, persistent disk, larger plans) are **not** created by this Blueprint and require your explicit choice.

## Estimated resources (measured locally on Windows 11, Python 3.12, demo project only)
* Memory (working set) after the demo workflow: API ≈ 94 MB, worker ≈ 82 MB. With the embedded worker both live in one process, so plan for ~200 MB plus headroom.
* Job durations: import ≤ 0.14 s, analysis ≤ 1.82 s (first run, includes Ruff start-up), generation ≤ 0.01 s, report (HTML + PDF) ≤ 0.33 s. Docker execution 4.1–6.3 s per run (not applicable on Render).
These are measurements for an 11-file project; real repositories will need more time and memory. The free plan suits evaluation; use `0.5c-512mb` or larger for regular use.
